# 项目取材与成稿

把现有项目变成值得阅读的文章，需要从工程材料里选出一个问题，并解释实现与取舍。取材范围由文章决定，不追求遍历整个仓库。

## 从哪里读起

先读适用的仓库说明，确认项目位置、当前分支或版本，以及是否有未提交改动。用 `rg --files` 和有针对性的搜索定位材料，排除构建产物、依赖目录和大体积生成文件。

通常先看 README、入口文件、依赖清单和配置示例，再沿文章主题读取关键实现、测试、设计文档及相关提交。它们回答的问题不同：

| 材料 | 可以支持 | 不能直接推出 |
| --- | --- | --- |
| README、项目介绍 | 声明的用途、使用方式和定位 | 所有功能均已实现、所有宣传指标均已验证 |
| 源码与配置 | 当前处理流程、接口、默认行为 | 作者当初为何这样做、线上实际效果 |
| 测试文件 | 被编写来验证的场景和预期 | 测试已经执行、生产问题不会发生 |
| 实际执行结果、日志、基准数据 | 指定条件下的观察结果 | 其他机器与工作负载下也成立 |
| 提交、PR、Issue、设计记录 | 可追溯的变化、讨论过的原因 | 所有中间尝试、实际投入时间和当时情绪 |
| 用户笔记或当次口述 | 作者提供的动机、经历、取舍与感受 | 笔记以外的戏剧性细节 |

README 与代码不一致时核对具体实现、配置和版本，把矛盾单独记下。区分已发布功能、工作区的新实现和计划项。只读到 README 时，降低文章对实现与效果的断言，不假装做过源码分析。

远程仓库沿用可用的 GitHub 连接器或仓库工具。读取不到关键内容时，说明缺失；不要从文件名想象实现。私有项目用于写稿不等于允许公开，正文只保留与解释相关、适合披露的信息，不带出凭据、内部地址和客户数据。

## 先建立简短的事实底稿

这是工作笔记，不必附在文章后，也不必创建独立文件。记录重要主张、证据位置及它允许怎样表述。例如：

| 主张 | 假设的材料 | 可写法 |
| --- | --- | --- |
| 请求按键去重 | 当前版本中存在对应条件分支与测试 | “相同键的请求会进入已有任务分支”，补充条件 |
| 新版本快一倍 | 只有一条提交消息，没有基准结果 | 不写性能倍数；可以写该提交调整了什么 |
| 曾尝试另一种架构 | PR 明确讨论并删除了相关实现 | 描述有记录的变更，不添加“折腾三天” |
| 选择这个库是为了易维护 | 只有依赖清单 | 写“项目使用了这个库”；维护收益若有依据，只能标为分析 |

源码位置记录路径与符号；有稳定公开仓库时可用 commit permalink。不要编造行号或把本机绝对路径当作公开博客链接。本文表格是示意，不能当作当前项目证据。

第一人称的“我做了”“我选择”需要用户材料或已确认的项目归属；即使项目归属已确认，“我当时以为”“我试了很多次”仍需要经历材料。没有这些信息，也可以写出完整的技术介绍。

## 选出文章主线

优先选择“某个约束怎样影响了方案”“一个功能背后最值得解释的机制”“某个故障如何被定位”。一句话能说清本文让读者理解什么，就足够开始写。

不要把仓库目录当作目录，不把全部依赖解释一遍，不替每个函数写说明。可从最重要的一次输入一路跟到输出，把影响结果的环节讲清。完整安装指南通常留在 README，正文只保留理解和试用所需的最小片段。

若项目包含多个独立主题，默认围绕证据最充分的一条完成文章，其余简短交代或链接；不自动扩成系列策划。

## 按证据写出初稿

- **先呈现问题或结果**：已有真实动机就使用；没有时描述项目面向的具体场景。
- **解释少数关键设计**：连接约束、实现和效果。历史选型有记录才写成作者的选择过程；从当前代码分析出的优缺点用分析语气。
- **给读者可核对的细节**：引用必要代码、命令、日志或已有截图，注明作用与条件。示意代码明确标注，不将其称为已测试的项目源码。
- **说明验证边界**：数据写明版本、环境、样本或工作负载以及来源。记录中已有测试结果可明确转述；自己没有跑过就不写“我实测”。对推测的性能原因使用合适限定。
- **停在当前状态**：实现、实验和计划分开写。限制可以放在对应方案旁边，不必人为制造“反思”章节。

缺失信息不影响主题时，省略或用中性表述继续写。只有缺失信息会改变核心事实、作者立场或主要结论时，提出少量针对性问题，同时整理不依赖答案的部分。没有失败记录时，不为填“踩坑”章节而提问或杜撰。

## 运行与文件边界

写文章以阅读材料为主。需要验证一个决定正文结论的命令时，先判断其依赖和副作用，选择最小本地验证；不为取材自行部署、触发外部任务或修改项目业务代码。

用户指定输出文件就写那里；位于博客工程时沿用内容目录。只有项目仓库且未指定位置时，可用 `blog-draft.md` 保存初稿，但先检查是否已存在，避免覆盖无关内容。用户只想在对话中看文章时直接返回正文。

不把发布授权、源码修复或 README 改造视为写稿请求的一部分。交付时简述文章主题、主要证据来源和仍会影响结论的缺口；一般无需展示整张事实底稿。
