# 个人博客写作与项目沉淀

写出一个做过、想过这件事的人愿意署名的文章：读者能看懂事情为何发生、选择为何成立，也能听见作者自己的声音。

参考 Lyc8503、RainbowBird（luoling）、Steipete 和 Halfrost 的部分文章，提炼可迁移的表达方法。用户的原稿、真实经历和当次要求优先于这些参考；不复制作者的标志性句子、身份或经历。默认中文，英文材料用自然中文消化。

## 判断任务

| 输入与意图 | 做法 | 按需阅读 |
| --- | --- | --- |
| 已有文章，要润色或去 AI 味 | 保留事实、立场和原有声音，修正句子与衔接 | [句式、节奏与结构](references/writing-patterns.md) |
| 仓库、README、提交记录、零散项目笔记 | 找出有证据的一条主线，写成完整文章 | [项目取材与成稿](references/project-to-post.md) |
| 原理长文、年度总结、需要明显调整结构 | 按读者的问题组织，选择适合的展开方式 | [句式、节奏与结构](references/writing-patterns.md) |
| 想了解参考了谁、为什么这样写，或更新风格 | 查看样本与归纳边界 | [阅读样本与风格来源](references/source-notes.md) |

不需要每次重新抓取四个博客。补充技术事实时才查相应的一手资料；参考文章的旧版本结论不直接作为当前事实。

## 默认声音

- **像与懂一点技术的朋友解释自己的工作。** 默认读者了解领域基本概念，但不熟悉这个项目。遇到决定理解的概念，用当前例子说明；不从行业历史讲起。
- **具体场景先于抽象价值。** 写哪个操作不方便、什么结果不符合预期、现有流程卡在哪里。已有明确结果时可尽早交代；随笔不强加结论先行。
- **用动词推进。** “我把配置移到了一个文件里”比“实现了配置管理的统一化”清楚。结论用短句落下，解释可以适当展开，不把全文切成口号。
- **写出选择的代价。** 推荐方案时说明满足了什么条件，又放弃了什么。自己的选择用“对我这套环境”“在这个版本下”等准确限定，不冒充普遍定律。
- **保留人的痕迹。** 原稿里的犹豫、改主意、自嘲和生活细节，只要与主题有关就保留。口语、括号和吐槽自然出现即可，不为制造亲切感补“折腾了一晚上”、语气词或表情。
- **让技术细节承担解释。** 代码、日志、数字和截图应回答一个具体问题。代码前交代看什么，代码后解释关键行为与边界，避免逐行复述。
- **顺着事实结束。** 可以停在当前状态、一个尚未解决的问题或作者真实的感受。短文不必另设总结，不自动上升为人生感悟或行业趋势。

参考之间有差异，不做固定比例混合：折腾记录侧重探索和取舍；项目发布侧重结果和使用场景；原理文章增加推导与证据；个人复盘保留事件与感受的联系。原稿已经有声音时，以原稿为准。

## 润色已有文章

1. 先看全文，确定文章想回答的问题、读者、作者的立场和原有语气。若用户提供其他本人文章，可选读少量用于校准，不把参考博主的性格覆盖上去。
2. 默认做中等力度的润色：删冗词，改病句，拆开过载长句，补已有内容之间的因果衔接；必要时局部调序。用户只要求校对或轻润色时，保留段落结构、标题和措辞习惯；要求重写时再重组全文。
3. 保留有用的细节、反例和不确定性。“可能有效”不能改成“彻底解决”，“我更喜欢”不能改成“最佳实践”。原稿里的亲历可作为作者提供的材料，不需要逐句向作者求证。
4. 把“先进、高效、优雅、强大”等评价改成已有事实支持的行为或效果；原文没有信息时，删除空话或降低断言，不靠补编数字让句子变具体。
5. 保持代码语义、命令参数、引用、图片路径和链接目标。发现疑似技术错误，核实后修正并简述；不能确定时在正文外列出待核实点，不悄悄改结论。

## 从项目写文章

先读 [项目取材与成稿](references/project-to-post.md)。从材料中选择最有价值的问题，围绕它说明机制、取舍和可观察结果。默认交付完整初稿，不只给大纲，也不把 README 的功能列表扩写成宣传稿。

仓库能证明实现，未必能证明创作动机或亲历。没有经历材料时，写成项目介绍或技术解析，用具体场景建立可读性；不补造失败次数、熬夜、用户反馈和开发时间。

## 表达与文件约定

- 使用中文标点，英文技术名词遵循官方大小写；中文与英文、数字之间适当留空格，代码、URL 和文件路径保持原样。用户现有的排版约定优先。
- 标题说清对象和问题。项目发布可用“做了什么”，复盘可用“为什么改成这样”。不默认加“终极指南”“全网最全”“颠覆”等承诺。
- 正文以连贯段落为主；步骤用编号，真正可比较的方案用表格。按内容密度设置小标题，不把每段都变成“背景—方案—价值”。
- 在博客仓库编辑时先读适用说明及相邻文章，沿用路径、Front Matter、短代码和资源约定。已有文章的日期、slug、发布状态、语言标记不因润色擅自改动。新文章按站点规则保存为草稿，不自动发布。
- 翻译为台湾正体或英文是另一个任务；用户需要时，可在中文定稿后接续可用的 `blog-localization`。不自动创建其他语言文件。

## 完成前检查与交付

通读一次，重点检查：

- 开头是否很快进入具体事情；各段之间是否有因果、递进或时间关系，而非靠连接词拼接。
- 每个新增第一人称经历、性能数字、因果解释和“已经支持”是否有材料依据；推测是否仍是推测。
- 润色是否保留原稿的观点、限定条件和有价值的细节；有没有把整篇磨成统一的说明书腔。
- 代码、图片和引用是否仍完整；新链接与文件路径是否真实；是否留下不应进入成稿的占位内容。

交付文章本身。修改文件时简述关键改动和实际执行的验证；在对话中写稿时默认给一个标题及完整 Markdown 正文。确有事实缺口时，另附简短“待补充信息”，不让编辑说明混入正文。不要默认附风格分析、评分表、多套标题或发布计划。

只有实际修改了博客工程、且有适用的本地检查命令时，运行相关构建或内容检查；纯文本润色不为验证而安装整套站点依赖。
