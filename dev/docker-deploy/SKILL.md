# /opt 下的 Docker Compose 项目

先从用户指定的目标、当前 Docker context 和项目所在文件系统确认主机。目标为 `10.0.30.100` 时，先读[主机运行约定](references/host-10.0.30.100.md)。其他主机按其实际项目目录、部署方式、地址池和服务例外操作。

## 识别实际部署

- 用 `docker ps` 找运行中的服务，用 `docker ps -a` 补齐已停止和一次性容器。从容器的 Compose 标签核对项目名、服务名、工作目录和配置文件。项目名可能与目录名不同。
- 在目标主机读取项目文件。后续所有 Compose 命令沿用实际部署的项目名、工作目录、按顺序传入的 `-f` 文件、环境文件和必要的插值变量。下文的 `docker compose` 均指这组调用参数。
- 用户问「哪些能更新」时只检查。读取本地运行镜像的 digest，并查询仓库中同一平台、同一层级的 manifest digest。分别列出有更新、已是当前版本、无法判定的服务；缺少可比 digest 或仓库不可访问时说明原因。检查期间不拉取、不改标签、不重建。

## 新增或修改项目

保留已有镜像、环境变量、端口、挂载和网络，改动限于用户要求或适用的主机规范。新项目可放在 `/opt/<name>/docker-compose.yaml`，省略 `version`。沿用已有项目的管理方式，尤其注意依赖宿主机网络的服务、一次性任务和发布目录的符号链接。

选择网络前，用 `docker network inspect` 查现有网络的驱动、IPAM 网段和连接关系。需要通过服务名互访的容器使用用户自定义网络。需要指定子网时，从目标主机的地址池中选择与 Docker 网络和主机路由均不重叠的网段。保留已有隔离网络。

用 `docker compose config -q` 验证实际配置，避免输出已展开的密码。用户要求部署新项目时用 `docker compose up -d` 启动并检查服务状态；仅整理文件时只验证配置。

## 更新运行中的服务

1. 从运行中容器确定更新范围。按服务记录容器的实际镜像 ID、配置使用的镜像引用、平台和健康状态。跳过本地构建且未发布的镜像。批量更新时保留已停止项目和服务的原状态。
2. 按镜像串行处理。每次只给一个服务执行 `docker compose pull --ignore-buildable --ignore-pull-failures --policy always <service>`。检查拉取输出和本地镜像 ID；忽略拉取失败的选项可能让命令在失败时仍返回成功。失败或跳过的镜像单列。
3. 对跟随 `:latest` 的 PostgreSQL、MySQL、MariaDB、Redis、PostGIS，先核对当前和候选镜像的软件主版本。PostGIS 同时核对 PostgreSQL 和扩展版本。主版本会跳或版本无法确认时，保留运行容器；若拉取已移动标签，把该标签指回先前记录的运行镜像 ID。同主版本按普通更新处理。
4. 候选镜像 ID 与运行容器不同时，执行 `docker compose up -d --pull never --no-build --no-deps <service>`。同一镜像由多个服务共用时，逐一判断并验证。镜像更新与资源清理分开执行。
5. 核对重建后实际镜像 ID，等待健康检查通过；无健康检查时使用项目已有的就绪检查。失败时先看日志及迁移状态。若数据格式兼容，将原镜像引用恢复到记录的旧 ID 后重建该服务，并再次验证；迁移不可逆或兼容性未明时，保留现场并报告故障。

## 清理镜像与卷

- 盘点目标主机上的现有 Compose 项目，包含停用项目、覆盖文件和可选 profiles。根据有效配置解析镜像引用和命名卷的实际名称，包含自定义 `name` 和外部卷。遇到无法读取或解析的项目时，保留无法排除被其使用的资源。
- 用全部容器（含已停止容器）的镜像 ID、镜像引用和挂载补齐保护范围。仅逐项删除未受保护的旧标签、悬空镜像，以及既未被项目声明又未被任何容器挂载的卷。删除前复核引用，按具体标签、ID 或卷名操作。避免全局 `docker image prune -a`、`docker volume prune` 和强制删除。

按用户使用的语言汇报。问「好了吗」时先答是否完成，再列出已更新、正在处理和失败或跳过的项目。
